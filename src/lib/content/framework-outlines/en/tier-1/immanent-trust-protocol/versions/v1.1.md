## Executive Summary

The Global Governance Frameworks (GGF) propose a bold vision for regenerative economics — Hearts and Leaves currencies, Proof of Care validation, nested economic coordination, and capture-resistant meta-governance. Several critical vulnerabilities remain underspecified:

- **Collusion rings** can fabricate care transactions to extract Hearts.
- **Sybil attacks** can inflate trust scores or capture participatory votes.
- **Proof of Care** lacks a verifiable, non-gamifiable mechanism.
- **Cross-BAZ trust** currently depends on manual relationships or centralised authorities.
- **Meta-governance capture** detection is described qualitatively, not quantitatively.

The **Immanent Trust Protocol (ITP)** closes these gaps. ITP is a post-consensus, observer-relative trust architecture that provides:

- **Trust Independence Metric (TIM):** Mathematically collapses collusion rings — a thousand Sybils endorsing each other have the influence of one honest node.
- **Trust Shock Propagation:** Endorsers have "skin in the game" — if a node defects, its endorsers' trust weight is temporarily held until restitution (adapted to restorative justice for GGF use).
- **Scale-Adaptive Fields (SAFs):** Ephemeral, auto-dissolving coordination structures for cross-BAZ decisions, with cryptographic time-to-live.
- **Local Trust State (LTS):** Each node computes its own trust assessment using only local information — no global ledger, no single point of control.

This document specifies how ITP integrates with the GGF's Financial Systems, AUBI, Nested Economies, and Meta-Governance frameworks. It includes a **GGF-specific adaptation profile** (restorative rather than punitive propagation) and a **three-phase implementation roadmap** (Hearts Treasury fraud → Proof of Care → meta-governance integrity).

## 1. What Is ITP? (A Short Overview for GGF Readers)

ITP is not a blockchain, a cryptocurrency, or a global reputation system. It is a **protocol for local, observer-relative trust** — each participant maintains its own **Informal Trust Ledger (ITL)**, a graph of cryptographically signed **Trust Signals** (interactions, endorsements, constraints). Trust is computed at the edge, using only the signals a node has received from its immediate neighbourhood.

**Core mechanisms relevant to the GGF:**

| ITP Mechanism | Purpose | GGF Analogue |
|---------------|---------|---------------|
| **Trust Signal** | A signed claim: "Node A interacted with Node B in context C, outcome value V, confidence X." | Proof of Care, Community Provider endorsement |
| **Local Trust State (LTS)** | Scalar trust score in [-1,1], computed locally from signals. | Per-contribution score; BAZ Council member trustworthiness |
| **Trust Independence Metric (TIM)** | Discounts endorsements from nodes with overlapping neighbourhoods. | Collusion ring detection (fake care logs, Sybil votes) |
| **Trust Shock Propagation** | Penalty cascades backward to endorsers when a node defects. | Endorser liability (without financial stake) |
| **Scale-Adaptive Field (SAF)** | Temporary, self-dissolving coordination structure with rotating coordinator. | Inter-BAZ ecological standard setting, crisis response |
| **Distance Attenuation** | Signals from far-away nodes are heavily discounted (λ=0 at 4+ hops). | Localism / subsidiarity — no global trust override |

**Key properties for the GGF:**
- **No global consensus** — each BAZ computes its own trust; no single ledger can be captured.
- **Sybil-resistant by topology** — TIM collapses collusion rings regardless of their size.
- **Endorser liability without financial stake** — reputational collateral is universal.
- **Ephemeral coordination** — SAFs prevent permanent bureaucratic capture.

## 2. GGF-Specific Adaptation Profile

ITP's default design uses punitive shock propagation and a protocol-agnostic signal schema. Several adaptations are needed for GGF deployment.

### 2.1 Restorative Hold (instead of permanent reduction)

ITP's default shock propagation permanently reduces endorsers' trust weight when a node defects. This conflicts with the GGF's restorative justice and Right Relationship principles. The GGF adaptation replaces punitive slashing with a **restorative hold** model.

When a verified defection occurs (e.g., fake care log, Hearts redemption fraud):

1. **Freeze** the trust weight of all direct endorsers of the defector. Their existing LTS contributions remain, but new signals from them are temporarily discounted (multiplier = 0.5).
2. **Notification** — the defector and endorsers enter a **resolution period** (default 30 days).
3. **Restitution** — if the defector makes amends (verified by the victim and a Community Weaver), endorsers' trust weight is fully restored.
4. **Only if restitution fails** and endorsers are proven to have colluded in the fraud, the weight reduction becomes permanent (slashed by Δ = confidence × severity).

This preserves the incentive for endorsers to vet nodes carefully, while allowing genuine mistakes or external shocks to be repaired.

**Adjudication pathway:** Disputes during the resolution period are handled by the institution closest to the context:
- **Within a BAZ:** The BAZ Council mediates, with Community Weavers facilitating.
- **Between BAZs:** The Digital Justice Tribunal (DJT) adjudicates, using the Kintsugi Protocol's restorative framework.
- **Involving intimate or gender-based harm:** The DJT's Chamber of the Guardian applies the Survivor Sovereignty Protocol.
- **Appeals:** Any party may appeal to the DJT within the 30-day hold period. The hold is extended until the appeal is resolved.

### 2.2 LMCI-A Scoring via Context URIs (not schema extension)

The AUBI framework requires multi-dimensional scoring (Love, Meaning, Connection). Rather than extending ITP's core signal schema with a GGF-specific vector — which would couple the protocol to one application — we use ITP's existing `context` field to separate dimensions:

| Context URI | What It Captures | Signal Value Meaning |
|-------------|-----------------|---------------------|
| `ggf:care:love` | Emotional care, companionship, presence | Quality of relational care (0 to 1) |
| `ggf:care:meaning` | Skill transfer, mentorship, purposeful work | Quality of developmental contribution (0 to 1) |
| `ggf:care:connection` | Community building, social bridging | Breadth and depth of social impact (0 to 1) |
| `ggf:ecology:leaves` | Ecological restoration, stewardship | Verified environmental outcome (0 to 1) |
| `ggf:treasury:redemption` | Hearts redemption request | Confidence only (value = amount) |
| `ggf:weaver:endorsement` | Community Weaver audit of a provider | Overall assessment (0 to 1) |

A single care act generates up to three Trust Signals (one per LMCI dimension), each in its own context. The AUBI policy layer aggregates these into an LMCI-A score. ITP's core schema remains unchanged — a scalar `value`, a `confidence`, a `context` URI.

### 2.3 Context Ontology and Registry

The GGF-specific context URIs are managed by the Social Resilience Council via a decentralised schema registry (per ITP Section 3.5). New contexts can be proposed by any BAZ; adoption requires endorsement by 5+ independent BAZs (TIM-verified). This prevents context farming (Section 12.2.2 of the whitepaper) while allowing the ontology to evolve.

### 2.4 Sybil-Filtered Voting for Governance (not trust-weighted)

**v1.0 proposed trust-weighted voting** — each person's vote weight proportional to their LTS. This is rejected for GGF use because it creates a plutocracy of reputation: early participants and well-connected nodes accumulate disproportionate influence, contradicting the GGF's equity commitments and the principle that every person's voice has equal worth.

Instead, the GGF uses **Sybil-filtered one-person-one-vote:**

1. Each BAZ resident has one vote.
2. Before a vote, TIM is applied to the set of registered voters. If a cluster of voters has high neighbourhood overlap (suggesting Sybil identities), their registrations are flagged for manual review by Community Weavers.
3. Voters whose registrations are confirmed (either by passing TIM or by Weaver review) each get exactly one vote of equal weight.
4. The vote proceeds as standard democratic process — no trust weighting.

This preserves democratic equality while using TIM for what it's designed for: detecting fake identities, not ranking legitimate ones.

**Exception:** For narrow technical decisions (e.g., setting TIM parameters, adjusting Hearts demurrage rate), a council of domain experts may use confidence-weighted input where each expert's confidence in their recommendation is visible to other voters. This is advisory, not binding — the final decision remains one-person-one-vote among the relevant council.

### 2.5 Love Ledger Privacy Separation

The Love Ledger captures non-monetised recognition (Gratitude Tokens). Making this data directly available as ITP Trust Signals risks a chilling effect: people may hesitate to express genuine gratitude if it becomes a cryptographic signal that affects someone's access to resources.

**The GGF adaptation enforces a strict separation:**

- **Love Ledger entries are NOT Trust Signals by default.** They exist in a separate data store with no automatic connection to the ITL.
- **Opt-in conversion:** A recipient may explicitly consent to convert a Love Ledger entry into a Trust Signal (via a signed conversion request). This is a one-time, per-entry decision — not a blanket setting.
- **Aggregate statistics only:** For LMCI-M (the population-level wellbeing metric), Love Ledger data is aggregated using zero-knowledge proofs (ITP Section 8.2) — proving that a community has N gratitude entries above a threshold without revealing who gave or received them.
- **No reverse inference:** ITP nodes cannot query the Love Ledger to find out who expressed gratitude to whom. The data flows one way: Love Ledger → (opt-in) → Trust Signal. Never the reverse.

This preserves the Love Ledger's character as a space for genuine, unjudged recognition while allowing people who want their care contributions to count toward their trust score to opt in.

### 2.6 Distance Attenuation: Security vs. Cooperation Tradeoff

ITP's default distance attenuation is λ(1) = 1.0, λ(2) = 0.5, λ(3) = 0.1, λ(4+) = 0.0. The GGF adaptation **keeps these defaults unchanged.** The rapid decay is a core security property — it bounds the influence of distant, unverifiable signals and ensures that trust remains local.

However, this means cross-BAZ trust pathways (A→B→C) are significantly attenuated: a signal traversing two hops arrives at 50% weight, and three hops at 10%. For inter-BAZ coordination, this is by design — distant BAZs should not have strong influence over local decisions. When stronger coordination is needed (e.g., a shared watershed), the correct mechanism is a Scale-Adaptive Field (Section 7 of the whitepaper), not weakened attenuation.

**Explicitly rejected:** Raising λ(2) to 0.7 as proposed in v1.0. The security cost (weaker Sybil resistance at two hops) is not justified by the social benefit (slightly easier cross-BAZ cooperation). SAFs provide the same coordination capability without compromising the trust model.

### 2.7 Architecture: ITP Gossip and Hyperledger Fabric

The AUBI framework (§10) specifies Hyperledger Fabric for its technical architecture. ITP's gossip-based propagation does not require — and is philosophically opposed to — ordered global consensus. These two layers must be clearly separated:

**Hyperledger Fabric** serves as the **settlement layer** for Hearts/Leaves transactions — transfers, redemptions, demurrage. It provides finality, auditability, and integration with existing financial systems. This is where the money moves.

**ITP gossip** serves as the **trust layer** — Trust Signals are propagated via relays (Nostr-style or libp2p gossipsub), stored locally by each node, and evaluated using LTS and TIM. No global ordering is needed. This is where trust is computed.

The two layers interact at well-defined points:
- The Hearts Treasury queries a node's local ITP state (LTS, TIM τ) before approving a Hyperledger redemption transaction.
- Community Provider chartering decisions are informed by ITP trust scores but executed as Hyperledger governance transactions.
- AUBI Layer 2 bonus calculations use ITP trust scores as input but the actual Hearts distribution is a Hyperledger transaction.

ITP does not replace Hyperledger; it provides the fraud-resistance layer that Hyperledger's consensus mechanism cannot (since Hyperledger trusts its permissioned validators, but those validators cannot detect Sybil collusion among application-level participants).

## 3. Vulnerability Mappings (How ITP Closes Each Gap)

### 3.1 Financial Systems Framework

| Vulnerability | ITP Mechanism | How It Solves |
|---------------|---------------|---------------|
| Hearts Treasury fraud — fake care logs | TIM | Fake recipients have overlapping neighbourhoods (all endorse the same fake provider). TIM discount τ → 0, so their collective redemption weight collapses. |
| Sybil rings manipulating Hearts supply | TIM + distance attenuation | Sybils cannot scale influence because their endorsements are discounted by TIM and also limited by hop distance (λ=0 beyond 3 hops). |
| Heartstarter match fund abuse | Velocity-limited accumulation + TIM | A new BAZ cannot reach high trust quickly (Δ_max = 0.05/day). Even with many fake transactions, TIM collapses the ring before it can extract match funds. |
| Love Ledger gamification (fake gratitude) | TIM (for opt-in converted signals only) | Fake gratitude accounts that opt in to Trust Signal conversion share identical neighbourhoods. TIM discounts them to zero. Entries that remain in the Love Ledger are not affected. |
| Inter-Currency Translation Layer capture | SAFs + TIM | Instead of a permanent ICTL committee, use a SAF for each rate change. SAF auto-dissolves after TTL; TIM ensures joining nodes are independent. |

### 3.2 Adaptive Universal Basic Income (AUBI)

| Vulnerability | ITP Mechanism | How It Solves |
|---------------|---------------|---------------|
| Proof of Care — fake provider rings | TIM | A provider with 1000 fake recipients: those recipients are Sybils with overlapping neighbourhoods. TIM collapses their collective endorsement weight. |
| Layer 2 bonus gaming | Trust Signal expiry + confidence cap | Each care act is a signed signal with expiry (90 days). Confidence is capped at 0.3 for low-stakes interactions. |
| Provider chartering without objective criteria | LTS threshold | A provider is charterable when LTS ≥ 0.7 from at least 5 independent recipients with TIM τ > 0.6. This is auditable. |
| BAZ Council capture (Sybil voters) | Sybil-filtered voting | TIM flags voter registrations with high neighbourhood overlap. Confirmed voters get equal votes. Sybil registrations are reviewed by Community Weavers. |
| Stateless population enrollment | Threshold attestation | 3+ Community Weavers with high LTS issue endorsements for the stateless person. No central authority required. |
| Cold-start / bootstrapping | Velocity-limited accumulation | Stage 1 interactions are logged as low-confidence Trust Signals (c_max = 0.3). A verifiable audit trail from day one. |

### 3.3 Nested Economies

| Vulnerability | ITP Mechanism | How It Solves |
|---------------|---------------|---------------|
| Cross-BAZ trust without global authority | Trust pathways + distance attenuation | BAZ A trusts BAZ C via a chain A→B→C. Attenuation at λ(2) = 0.5, λ(3) = 0.1. Long chains have negligible influence — keeps trust local. When stronger coordination is needed, a SAF forms. |
| Community Weaver verification quality | Trust Signals from trainees | Each trainee issues an `interaction` signal after training. A Weaver's LTS reflects successful trainees. Low-quality Weavers lose weight. |
| 10% solidarity redistribution fairness | TIM-verified governance | Redistribution amount is a policy decision by the SRC. ITP ensures the SRC itself is not captured (Sybil-filtered voting), making the redistribution decision legitimate. |
| Participatory budgeting Sybil attacks | Sybil-filtered voting | TIM flags suspect registrations. Confirmed participants get equal votes in budgeting. |

### 3.4 Meta-Governance

| Vulnerability | ITP Mechanism | How It Solves |
|---------------|---------------|---------------|
| Institutional capture of councils | TIM + Sybil-filtered voting | Capture requires controlling many independent identities that pass TIM. The four-criteria Accountable Coordination audit becomes computationally measurable. |
| Conscious refuser retaliation | Restorative hold | If a council penalises a refuser, the refuser (or their endorsers) can issue `constraint` signals. The council's decision enters a restorative hold, adjudicated by the DJT. |
| System Canary ignored | High-weight warning signals | Canaries are certified nodes whose `warning` signals are weighted by their LTS. Ignoring them triggers automatic integrity review. |
| Permanent coordination structures (capture risk) | SAFs with TTL | Every meta-governance working group is a SAF that auto-dissolves after TTL. Renewal requires active re-endorsement by threshold independent members. |

## 4. Implementation Phases

ITP integration is designed to be incremental, respecting the GGF's existing BAZ Starter Pack and phased rollout.

### Phase 1 (Year 1–2): Hearts Treasury Integrity

**Goal:** Prevent fraud in Hearts redemption and Heartstarter matching.

**Deliverables:**
- Deploy a lightweight ITP relay network (Nostr-style) for the pilot BAZs.
- Implement TIM for the set of recipients endorsing a Community Provider.
- Hearts Treasury (on Hyperledger Fabric) queries local ITP node before approving redemptions: require τ > 0.6 for any redemption above a threshold (e.g., 100 Hearts).
- Heartstarter match fund releases second tranche only after TIM-verified independent endorsements.

**Success metrics:**
- Zero successful collusion-based fraud in pilot (target: 100% detection of rings with θ > 0.5).
- Additional latency for redemption `<` 2 seconds.

**GGF components affected:** Financial Systems §15 (Hearts Treasury), AUBI §7.4 (Heartstarter).

### Phase 2 (Year 2–3): Proof of Care and AUBI Layer 2

**Goal:** Replace manual / AI-only verification with cryptographic trust for care and ecological contributions.

**Deliverables:**
- Community Providers collect signed Trust Signals from recipients for each care act, using context URIs (`ggf:care:love`, `ggf:care:meaning`, `ggf:care:connection`).
- AUBI Layer 2 bonuses are calculated from aggregated LTS of the provider across all recipients and dimensions.
- Community Weavers issue `ggf:weaver:endorsement` signals for providers they audit; these are weighted by the Weaver's own LTS.
- Implement restorative hold (GGF profile) with DJT as appeals body.
- Love Ledger privacy separation deployed: opt-in conversion with ZK aggregate statistics.

**Success metrics:**
- 90% of care acts logged as Trust Signals in pilot BAZs.
- Reduction in Layer 2 bonus disputes by >80%.

**GGF components affected:** AUBI §5.2 (Layer 2), Nested Economies §8 (Community Weavers), Financial Systems §3 (Love Ledger).

### Phase 3 (Year 3–5): Meta-Governance and Cross-BAZ Coordination

**Goal:** Enable Sybil-filtered voting, capture-resistant councils, and ephemeral Scale-Adaptive Fields for inter-BAZ decisions.

**Deliverables:**
- BAZ Council elections and SRC decisions use Sybil-filtered one-person-one-vote (TIM flags suspect registrations; Community Weavers adjudicate).
- ICTL structural changes (Tier B) are managed via SAFs — a temporary field forms, sets the new rate, then auto-dissolves after TTL (e.g., 90 days).
- System Canary nodes are certified and their `warning` signals trigger automatic integrity reviews.
- Accountable Coordination Audits include TIM analysis of council member endorsement patterns.

**Success metrics:**
- Four-criteria Accountable Coordination audit pass rate ≥ 95% for all councils.
- SAF formation time for inter-BAZ decisions `<` 1 hour.
- Zero successful capture attempts detected over 2 years.

**GGF components affected:** Meta-Governance (all layers), Nested Economies §5.3 (Adaptive Governance), Financial Systems §14 (ICTL).

## 5. Integration with Existing GGF Mechanisms

| GGF Mechanism | ITP Integration Point | Data Flow |
|---------------|----------------------|-----------|
| **Love Ledger** | Separate data store. Entries are NOT Trust Signals unless recipient opts in via signed conversion. ZK proofs aggregate statistics for LMCI-M. | Love Ledger → (opt-in) → Trust Signal → ITL → TIM. Never reverse. |
| **Hearts Treasury** | Before redeeming Hearts, the Treasury's Hyperledger chaincode queries the provider's local ITP node for LTS and TIM τ of the recipient set. | Provider submits redemption → Hyperledger queries ITP → approve/reject → settle on Hyperledger. |
| **Proof of Care** | Implemented as signed `interaction` Trust Signals from recipient to provider in the appropriate `ggf:care:*` context. | Recipient signs signal → gossip propagation → stored in provider's and evaluator's local ITL. |
| **Community Weavers** | Weavers are ITP nodes whose LTS is built from trainee interaction signals. Their endorsements carry weight proportional to that LTS. | Weaver audits provider → issues `ggf:weaver:endorsement` → included in TIM computation for the provider. |
| **BAZ Council** | Council elections use Sybil-filtered one-person-one-vote. Each voter's registration is checked against TIM; flagged registrations are reviewed by Weavers. | Registration set → TIM analysis → flags → Weaver review → confirmed voters → equal-weight vote. |
| **Social Resilience Council** | Uses Sybil-filtered voting. Temporary working groups are SAFs with TTL. | SRC decision → SAF forms if cross-BAZ coordination needed → TTL expires → SAF dissolves. |

## 6. Cryptographic and Governance Requirements

### 6.1 Technical Requirements

- **Relay infrastructure:** At least 3–5 community-run relays per BAZ (Nostr or libp2p). No central relay. Relays are independent of the Hyperledger Fabric network.
- **Key management:** Each participant (adult resident, Community Provider, Weaver) generates an Ed25519 key pair. Keys can be rotated with attestation (ITP Section 8.3.4).
- **Storage:** Each node stores signals for at least 90 days (expiry). Relays may store longer for archival.
- **TIM parameters:** d_max = 100, k_sample = 50, α = 0.7, τ_threshold = 0.6 for trust decisions.
- **Hyperledger integration:** ITP nodes expose a read-only query interface that Hyperledger chaincode can call. No write access from Hyperledger to ITP.

### 6.2 Governance Requirements

- **Social Resilience Council** must adopt a resolution to recognise ITP-based trust scores as valid input for Hearts Treasury and AUBI Layer 2 decisions.
- **Data sovereignty:** BAZs may choose to run their own relays and not share signals outside the bioregion (privacy mode).
- **Appeals process:** The Digital Justice Tribunal handles disputes about false Trust Signals. The restorative hold ensures no permanent damage before resolution. The Kintsugi Protocol's restorative framework applies to all ITP-related disputes involving personal harm.
- **Annual audit:** The Accountable Coordination Audit must include verification that TIM parameters are not being manipulated to exclude legitimate participants.
- **Love Ledger governance:** The SRC sets policy for opt-in conversion rates and ZK aggregation parameters. Changes require Sybil-filtered vote of the SRC.

### 6.3 GGF-Specific Parameter Recommendations

| Parameter | ITP Default | GGF Adaptation | Rationale |
|-----------|-------------|----------------|-----------|
| Shock propagation | Punitive (permanent reduction) | Restorative hold (30-day freeze) | Aligns with Right Relationship; adjudicated by DJT |
| Distance attenuation λ(2) | 0.5 | **0.5 (unchanged)** | Security property preserved; cross-BAZ coordination uses SAFs instead |
| Minimum endorsers for provider chartering | 1 | 5 independent (TIM τ > 0.6) | Prevents lone-endorser fraud |
| TIM τ threshold for redemption | 0.0 (any) | τ > 0.6 required | Allows some natural overlap but blocks coordinated collusion |
| Trust Signal expiry | 1 year | 90 days for care acts; 1 year for ecological attestations | Care requires fresh verification; ecological outcomes are slower |
| Love Ledger → Trust Signal | N/A (not in ITP) | Opt-in only, per-entry consent | Prevents chilling effect on genuine gratitude |
| Restorative hold period | N/A | 30 days, extendable by DJT | Sufficient for most disputes; complex cases get extensions |

## Conclusion

The Immanent Trust Protocol provides the missing cryptographic and game-theoretic foundation for the GGF's regenerative economic vision. By integrating ITP, the GGF gains:

- **Provable collusion resistance** (TIM theorem) — not heuristic detection, but a mathematical guarantee that Sybil rings cannot scale influence.
- **Universal endorser liability** without financial stake — aligning incentives for Community Providers and Weavers through reputational collateral, enforced within a restorative justice framework.
- **Ephemeral, capture-resistant coordination** (SAFs) — replacing permanent institutions with auto-dissolving structures that cannot outlive their mandate.
- **Observer-relative trust** — preserving local sovereignty while enabling cross-BAZ cooperation through trust pathways, not global authorities.
- **Democratic integrity** — Sybil-filtered voting that preserves one-person-one-vote equality while making fake identities detectable.

The GGF adaptation profile ensures that these technical mechanisms operate within a restorative justice framework, honouring Indigenous principles and Right Relationship. ITP provides the trust substrate; the GGF provides the governance, economics, and ethical architecture built on top of it. Neither is complete without the other.
