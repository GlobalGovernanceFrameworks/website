## このコードベースについて

このサイトは [SvelteKit](https://kit.svelte.dev) アプリケーションで、相互に関連する数十のガバナンスフレームワークを3言語で公開しています。複雑さの大部分はUIにあるのではなく、コンテンツ、メタデータ、ナビゲーション、翻訳がどのように互いに同期を保つかにあります。

**技術スタック:**

- **SvelteKit** — ルーティング、SSR、アプリケーション全体
- **mdsvex** — 長文のフレームワークドキュメント用のMarkdown処理
- **カスタムCSS** — Tailwindやユーティリティフレームワークは不使用。パレットにはCSSカスタムプロパティを使用し、コンポーネントスコープのスタイル。
- **カスタムi18n** — `src/lib/i18n/` にある小さなストアベースのシステム。ロケールごとのJSON翻訳ファイル
- **カスタムスキーマ** — `src/lib/schema/_index.ts` がフレームワークメタデータの唯一の信頼できる情報源

このうち2つは、当然と思うかもしれない前提に反するため強調しておきます。ここにはTailwindは一切ありません。Tailwindに言及している古いドキュメントは時代遅れです。また、スキーマは権威ある情報源であり、タイトル、階層、関連フレームワーク、公開状態はすべてそこから導出されます。もしどこかでフレームワークの並行リストを保守している自分に気づいたら、それはパターンではなくバグです。

## セットアップ

```bash
git clone https://github.com/GlobalGovernanceFrameworks/website.git
cd website
npm install
npm run dev -- --open
```

これで `http://localhost:5173` でサイトが立ち上がるはずです。Node 18以上が必要です。

もし開発サーバーがスキーマバリデーションで文句を言ってきたら、何かを壊したと決めつける前に出力を読んでください。 `validate-schema.js` はブロックエラーと健全性警告を区別し、健全性警告は既存のものです。

## ファイル構成

```
src/
├── lib/
│   ├── components/     再利用可能なSvelteコンポーネント
│   ├── content/        ロケールごとに整理されたMarkdownコンテンツ
│   ├── i18n/           翻訳システム + en/ sv/ ja/ JSONファイル
│   ├── schema/         _index.ts — フレームワークの正式なメタデータ
│   └── utils/
└── routes/             SvelteKitページ
```

フレームワークページは、手書きではなく大部分が生成されます。動的ルート `[slug]` がアウトラインモードと本文モードの両方を処理するため、フレームワークを追加するには通常、スキーマエンティティとコンテンツファイルを追加するだけで、ルートフォルダを作成する必要はありません。

## 初めてのPRの前に知っておくべき規約

**スタイリング。** ハードコードされた16進値ではなく、既存のカスタムプロパティ（`--primary-blue`、`--warm-gold`、`--content-text` など）を使用して、コンポーネントスコープのCSSを書いてください。ユーティリティクラスを導入しないでください。

**テキスト。** ユーザーに見える文字列は、コンポーネントに直接書かずにi18nのJSONファイルに格納します。新しい文字列にはすべて英語、スウェーデン語、日本語が必要です。もし1つしか用意できない場合は、英語を追加してPRでその旨を伝えてください。不足している翻訳はシステムが処理できる既知の状態ですが、コンポーネントにハードコードされた英語文字列は、3分の2の読者にとって見えない破損です。

**スウェーデン語の大文字化。** スウェーデン語ではタイトルケースを使いません。見出しの最初の単語と固有名詞のみ大文字にします。

**Markdownの落とし穴。** mdsvexでは、裸の `<` が数字の直前に来るとタグの開始と解析され、コンパイルに失敗します。バッククォートのコードスパンで囲んでください。HTMLエンティティは機能しません。remarkがSvelteコンパイラ実行前にそれらをデコードするからです。

## 着手しやすい場所

現時点で最も役立つ貢献は地味なものです。アクセシビリティの修正、レスポンシブレイアウトの問題、デッドコード、そしてプロジェクトの実態と比べて内容が古くなってしまったページ。最後のカテゴリが多くあります。

もっと本格的なものをお考えなら、作り始める前にアイデアを説明するIssueを立ててください。アーキテクチャにはいくつかの設計思想が組み込まれており、後から大きなPRを解きほぐすよりも、最初にアプローチを議論する方が簡単です。

## 作業の提出

`main` ブランチに対してフォークし、ブランチを作成し、プルリクエストを開いてください。プルリクエストは焦点を絞ってください。1つのPRに1つの関心事がある方が、ごちゃ混ぜのものよりずっと速くレビューされます。

レビューは一人で行っているため、応答時間はまちまちです。しばらく放置されている場合は、Discordで軽く促してもらっても構いません。迷惑ではなく歓迎です。

## ヘルプを得る

質問にはDiscordが最も早い経路で、規模が小さいため、通常はあなたが尋ねているコードを書いた本人から回答を得られます。GitHub Issueも機能しますし、記録に残す価値のあることにはそちらの方が適しています。
